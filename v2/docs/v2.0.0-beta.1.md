# SSH Key Manager v2.0.0-beta.1

This is the first public V2 prerelease. It is intentionally installed side-by-side as `skm2`; production `skm` v1 is not replaced.

## What V2 changes

V2 replaces the v1 compressed model with explicit fleet concepts:

- Subject → Credential, so key rotation does not change identity.
- Node → Principal → Route, so machine identity is separate from SSH account and connection path.
- Desired policy → live observation → plan → apply, with optimistic revision checks.
- A dedicated restricted control-plane credential, separate from user/application access.

## Security model

- Private keys are never stored in fleet state or backups.
- SSH transport is delegated to the system OpenSSH client.
- Migrated host-key pins are enforced fail-closed.
- V2 uses a separate controller key (`~/.ssh/id_ed25519_skm2` by default).
- Enrollment installs that key with a forced command and `restrict`; it cannot open a generic shell.
- Remote mutation is available only through the daemonless bridge protocol.
- Apply checks both fleet revision and remote `authorized_keys`/managed-state revision.
- The bridge checks the remote revision twice, refuses symlinked state, locks mutations, backs up state and replaces files atomically.
- V2 never infers ownership from SSH key comments. Managed fingerprints live in a separate protected sidecar.
- External/unmanaged credentials are preserved, including in authoritative mode.

## Included in beta.1

- deterministic V1 metadata migration;
- migrated pinned host trust;
- stable namespace-separated IDs;
- Subjects and Credentials;
- Nodes, Principals and direct Routes;
- observe/additive/authoritative policy model;
- restricted enrollment and reversible unenrollment;
- live inspect;
- plan and explicit apply;
- stale-plan rejection;
- revision-guarded rollback;
- operation history;
- full-state backup/restore without private keys;
- Linux amd64/arm64 and macOS amd64/arm64 binaries;
- SHA-256 release checksums, release manifest and GitHub build-provenance attestations.

## Real-fleet validation

Before this prerelease was tagged, the V2 lifecycle was exercised between a Raspberry Pi controller and a macOS target using the existing V1 fleet metadata:

1. V1 → V2 migration preserved 6 Subjects, 6 Credentials, 2 Nodes, 8 policy rules and the pinned Mac host key.
2. Restricted V2 enrollment succeeded.
3. The V2 controller key was proven unable to execute an arbitrary SSH command.
4. A temporary service credential produced exactly one planned grant and no revoke.
5. Apply granted real SSH access and marked only that credential as V2-managed.
6. Reusing the stale plan was rejected by remote revision mismatch.
7. Rollback removed the temporary credential and restored managed ownership state.
8. The rolled-back credential could no longer authenticate.
9. Unenrollment removed the V2 control-plane key.
10. The target `authorized_keys` matched the pre-enrollment backup byte-for-byte.
11. V1 policy, audit and doctor returned clean after the test.

## Known beta.1 limitations

- Controller execution currently uses direct routes only. Tailscale, SSH-config and ProxyJump route types are modelled but not yet executed.
- Host-trust discovery and rotation commands are not yet exposed in the V2 CLI.
- Subject/Node groups and first-class credential rotation/retirement workflows are not yet exposed.
- Multi-node resume/automatic rollback orchestration is not yet complete.
- `plan --node` still reports an informational warning for other unobserved fleet principals; it does not plan changes for them.
- Interactive TUI, Homebrew/package-manager distribution and final update UX are not yet complete.

## Installation

For beta testing, use the versioned release installer from this branch or download the matching release asset directly. The installer verifies the release checksum and the embedded binary version before replacing an existing `skm2` binary.

V1 and V2 may coexist. During V2 enrollment, v1 audit will report the dedicated V2 controller fingerprint as unknown because v1 intentionally does not know about V2 control-plane state. After V2 unenrollment, v1 audit should return clean again.
